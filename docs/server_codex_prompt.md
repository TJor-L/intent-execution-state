# UCSF 主开发与验证交接提示词

请在 UCSF 授权服务器上的 `intent-execution-state` 仓库继续工作。
首次接手预期 Git 提交：`{{COMMIT_SHA}}`

用户已明确要求将开发和测试重心移到服务器，提高推进效率。你现在是项目的主要
实现与测试 agent：在服务器连续完成检查、编码、合成测试、小规模真实验证、诊断和
修复。**不要只做设计审核或列出代码需求就交回 Mac。** 旧提示词“本轮仅审核、等待
Mac 实现”的安排已被本次指令取代。Mac 负责方案讨论、代码复核和里程碑反馈。

## 1. 接手已有状态

- 阅读 `AGENTS.md`、`docs/16_remote_development.md`、
  `docs/24_bounded_run_findings.md`、`docs/25_coherent_access_design.md`，以及需要时的
  `docs/22_bounded_feasibility.md`。历史文档记录当时状态，不要求重做已完成检查。
- 核对工作区和首次接手 SHA，保留已有私有配置、审核证据、两个 limited 报告及未提交
  工作。不要 reset 或覆盖已有改动；先判断归属并正常整合。
- 已有依赖环境优先复用；仅在依赖或环境需要时 `make setup`。如果当前版本尚未在
  此环境验证，运行 `make check`；无需把此前相同代码的成功检查反复从头执行。
- 初始 SHA 只标记接手版本。你可以继续修改、测试并生成新提交；后续真实任务应绑定
  你实际验证过的新提交，不要误把初始 SHA 当成永远不能变化的版本。

已知状态：合成 pipeline 和三来源有界验证器已实现，最近 Linux CI 172 项测试通过。
两次真实 CPU 运行得到有效 limited 报告，独立分片前缀没有共同身份覆盖。这不代表
真实关联不存在。预算诊断已实现；一致来源／精确键读取器目前只有设计，尚未实现。

## 2. 当前目标：在服务器打通一次有意义的关联验证

先利用已有获准资料和受限元数据核实可行的访问方式，再**直接实现一个实际可用的
后端**。优先复用现有一致来源清单或精确键索引；不要为了实现抽象框架同时开发所有
后端。docs/25 是起点，可以根据服务器证据修订具体接口，但需保留科学与数据边界。

连续完成以下步骤，无需在步骤之间等待 Mac：

1. 明确现成医嘱种子来源、身份域、确定性的选择规则和来源版本。确认能否找全这些
   键的关联医嘱、给药和观测记录，而不是任取三个来源的前几行。
2. 在仓库实现可复用读取器、配置契约和必要的 CPU 执行入口。真实字段、路径、动作、
   证据和清单留在被忽略的服务器配置；可提交代码和测试只能使用通用逻辑名及合成值。
3. 用生成的跨分片数据测试：关联位于前缀之外、种子之外的重复医嘱、重复给药、患者
   不符、回填记录、完整空查询与不完整查询、扫描行和保留行的独立上限，以及映射／
   清单／来源版本变化。已有时间与删失规则继续生效。
4. 完成关键测试后，在服务器核实映射语义、完整性证明、来源版本和资源预算；这些
   是基于证据的工程核实，**不是每一步都需要用户再次确认的流程**。已有权限和已审核
   事实可复用，无需反复要求用户提供同样信息。
5. 相关代码通过 `make check` 和 `make demo` 后提交为干净版本，在现有获准的小规模
   CPU/Slurm 范围内运行汇总验证。监控至终态，结合报告与 squeue/sacct 判断状态。
6. 普通代码、配置或调度缺陷由你直接修复并重测。每次重跑要有具体修复或新证据；
   不重复无变化的独立前缀扫描，不靠自动扩配额把 limited 变成 complete。

若现有访问能力足够，不要停在“建议下一轮实现”。推进到实现、测试和真实受限验证
完成，再做一次里程碑交接。如果运行仍是 limited，如实报告覆盖缺口，不能声称构建
了可靠 cohort；如果检查发现当前环境根本无法提供所需访问能力，按下面的阻碍处理。

## 3. 在哪里继续，在哪里需要外部输入

普通实现选择、单元测试、调试、已有权限内的有界只读检查、符合现有限额的 CPU
验证和修复后重跑，都在本次持续工作范围内，直接推进。

遇到以下实际阻碍，先完成不依赖它的代码、合成测试和具体方案，再报告最少需要的
外部输入：缺少访问权限／必要时间语义；无可证明覆盖的访问路径；必须新建持久化
索引／一致提取或做全源扫描；需要超出现有范围的计算资源或改变研究终点。
如果新准备操作确实不可避免，列明输入范围、方法、预计扫描/I/O/CPU/存储成本、
限制、产物存放及验收标准。不要只写“请 Mac 继续开发”，也不要把全量扫描藏在
所谓 probe 里。转移开发地点不代表扩大这些操作的范围。

## 4. 测试、版本与发布

- 编辑过程中运行针对性测试；pipeline 变更完成后运行 `make check` 和 `make demo`。
  不为文档小改动或无代码变化重复临床任务，不反复安装未改变的环境。
- 真实任务始终使用实际干净提交和固定映射／来源清单。开发 checkout 与排队／运行
  中的任务 checkout 分开，或等任务结束后再编辑；不要修改任务正在使用的配置。
- 小步骤可在服务器正常提交，但不要求用户每提交一次就来回 pull。同一分支只保留
  一个主要写入方；本轮由服务器负责实现，Mac 先做复核，避免双端竞争修改。
- 达到里程碑后更新实现状态和 `docs/20_research_log.md`，检查 Git diff 只含通用代码、
  合成测试与获准摘要，使用 `scripts/publish.sh` 普通推送并确认 CI。不要强推。
- 汇报代码 SHA、实现内容、测试、真实任务状态、覆盖限制与下一步。只要当前授权范围
  内还有明确可做的工作，就继续；不要为了凑一次交接而停在普通错误或设计阶段。

## 5. 数据和研究边界

临床记录、标识、真实值、原始 schema、日志、权重、私有路径、证据引用和已填清单
全部留在 UCSF 授权存储。Git 只推通用代码、合成测试、空白配置及审核后的操作摘要。
真实验证仍只输出受限汇总，不导出患者级 cohort、不传回 Mac；不猜测未确认的时间
或动作语义。患者不符、重复给药、回填／未知记录按既有规则拒绝；覆盖不足不推断
无给药或删失。检验特征、GPU、大规模训练和临床效应结论不属于当前可行性里程碑。
